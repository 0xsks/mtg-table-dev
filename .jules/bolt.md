## 2024-05-18 - Search loop property caching optimization
**Learning:** `searchCards` heavily relies on runtime string normalization, array allocations, and functional methods applied to ~35k+ cards in the tightest possible loop during card searches. The overhead of doing this during the request was significant, but could be offloaded almost entirely to server startup data processing. `localeCompare` in sorting `hits` in node.js was identified to be remarkably slower compared to pure string comparative operators (e.g., `<` and `>`).
**Action:** When performing searches over massive in-memory datasets, process values (such as lowercase strings, joined/sorted colors arrays) in advance and modify sorting mechanisms away from built-in globalization-aware operators where performance matters. Always pre-parse the user query matching constraints outside the loop entirely to reduce per-item logic overhead.
